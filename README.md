## Overview

This project provides a controlled environment for developing and validating cybersecurity testing and detection workflows.

The emphasis is not simply on executing security-related actions, but on demonstrating the complete process:

1. Define the expected behaviour.
2. Execute a controlled test.
3. Collect relevant telemetry.
4. Analyse the resulting data.
5. Validate whether the expected detection occurred.
6. Record the result.
7. Identify opportunities for improvement.

This approach reflects practical security operations and detection engineering principles, where repeatability, evidence, validation, and documentation are as important as the initial test itself.

## Metadata and Runtime State

The application uses:

```python
METADATA_FILE = "metadata.json"
```

This constant identifies the local metadata file used by the application.

The file is intentionally excluded from version control through `.gitignore`:

```gitignore
metadata.json
```

### Why is `metadata.json` ignored?

`metadata.json` represents local/runtime state rather than source code.

Depending on the implementation, it may contain information such as:

* Test execution state
* Locally generated identifiers
* Timestamps
* Previous execution information
* Runtime metadata
* Environment-specific values

Because this information may vary between environments and executions, it should not normally be committed to the repository.

### Important distinction

`.gitignore` and `METADATA_FILE` serve different purposes.

`.gitignore` controls **what Git tracks**.

```gitignore
metadata.json
```

`METADATA_FILE` controls **which file the Python application uses**.

```python
METADATA_FILE = "metadata.json"
```

Therefore, the presence of `metadata.json` in `.gitignore` is **not a reason to remove `METADATA_FILE`**.

The application can continue using the local file while Git prevents it from being committed.

### Recommended Test Coverage

Tests should progressively cover:

* Configuration handling
* Metadata loading
* Metadata creation
* Invalid metadata
* Missing files
* Error handling
* Input validation
* Core application functions
* Expected security-test results
* Unexpected results
* Edge cases

### Example Test Philosophy

A useful test should establish:

```text
Input
  ↓
Function / Component
  ↓
Expected Behaviour
  ↓
Observed Result
  ↓
Pass / Fail
```

Testing should focus not only on whether the code executes successfully, but also whether it behaves correctly when presented with unexpected or invalid conditions.

## Design Principles

The project follows several practical engineering principles.

### Repeatability

Security tests should produce repeatable results whenever possible.

### Evidence-Based Validation

Detection effectiveness should be assessed using observable evidence rather than assumptions.

### Separation of Concerns

Testing, configuration, metadata, and reporting should remain logically separated where practical.

### Defensive Focus

The project emphasises understanding and validating security controls, telemetry, detection logic, and response workflows.

### Documentation

Important decisions, test results, assumptions, and limitations should be documented.

### Fail Safely

Unexpected conditions should be handled explicitly rather than silently ignored.
